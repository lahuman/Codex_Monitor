# Desktop identity and release workflow

The visible product is Codex Monitor 0.1.10. Product name/version come from desktop/src-tauri/tauri.conf.json, shared with the embedded about dialog. The internal bundle identifier remains local.codex-lb.desktop.preview so existing account and history storage remains available. Technical Cargo/npm package names remain stable. The original SVG quota-ring/check/status icon follows the warm dashboard palette; macOS representations are generated with the installed Tauri CLI. ICNS chunks are parsed and sorted by their four-byte type at the generation owner, retaining unchanged image data and producing identical files on consecutive runs. No third-party brand mark is used.

## Build and installation

Prepare dependencies with frontend bun install --frozen-lockfile and desktop npm ci. Use npm run dev inside desktop for development, npm run build for an optimized app, npm run build:preview for debug, and npm run package:macos for a distributable build. Packaging regenerates icons, builds the app, reads actual bundle name/version/identifier, detects Mach-O architectures, and creates desktop/releases/<version>/macos-<architecture>/. This retains only versioned DMG and ZIP, SHA256SUMS.txt and release.json. After archive verification and publication, packaging deletes its installer/verification copies and the build bundle to avoid duplicate entries in macOS app discovery. Explicit npm run build retains an unpacked app for development. Installed apps and user-mounted volumes are never packaging cleanup targets. Failures before archive publication retain the source build; uncertain DMG cleanup retains its staging as before. The DMG contains an Applications symlink and installation instructions. The app includes the upstream MIT license text. Drag the app to Applications after quitting an older running copy. Existing release folders are never silently overwritten. Intel output can be built on an appropriate toolchain but only Apple Silicon was produced and tested here.

The minimum macOS setting is 13.3, aligned with the Safari 16.4 baseline of Tailwind CSS v4 (https://tailwindcss.com/docs/compatibility). This is a configured minimum, not a claim of testing every OS version. Actual QA used the current local Mac.

## Windows packaging

Native Windows x64 packaging uses NSIS, the configured product identity and a generated ICO. Windows tray observations use an explicit icon, UTF-16-bounded tooltip and the existing full account menu because tray titles are unsupported. File contents are synchronized before atomic replacement on both platforms; parent-directory synchronization is Unix-only.

Example: two successive vault writes are reloaded after restart without Windows directory-open failures. Tests run on the configured Windows Actions runner, but native execution and actual PC installation remain unverified until that workflow/user check succeeds. No Windows build or signed installer is claimed from the current Mac session.

## Native installation progress (0.1.4)

Finder owns drag-copy feedback; an 11 MiB app may copy before its progress window is shown. DMGs now retain drag installation and include 설치하기.pkg as an optional native Installer flow with standard stages/progress/completion. pkgbuild analyzes the verified app, explicitly disables relocation, checks version/identifier and atomically replaces the app bundle via upgrade semantics. productbuild synthesizes OS/architecture requirements from the actual build. No custom installer scripts, account payload or host installation are involved in packaging. The package is unsigned; app ad-hoc signing does not sign the installer. Users should quit the app before installing and may need native administrator authorization.

The component payload is expanded and strict-verified, compared against its source, constrained to the single app at /Applications, and inspected for scripts/relocation/OS/architecture/version. A read-only DMG round-trip rechecks package bytes and expanded contents. This establishes package construction and payload integrity, not a completed installation on the user's system. Existing runtime, accounts and release archives remain unchanged.

## Installation trust guidance in 0.1.10

The package producer now owns a single Korean/English offline guide used by the visible DMG HTML, plain-text instructions and native Installer welcome/completion pages. It is outside the app so the user can read it even before the package is allowed to open. It shows actual signing/ticket/Gatekeeper facts, explains inability to verify malware absence, and links to Apple's conditional app-specific Open Anyway procedure. Detected malware, damage, revoked trust and failed integrity checks require stopping. No protection settings, quarantine, user accounts or app execution are changed by the guide. Example: a recipient sees the unverified-malware warning, opens 먼저 읽어주세요.html in the DMG, verifies origin, and follows the documented manual per-app procedure if appropriate. Installer payload remains app-only and script-free.

## Windows Releases publication

The earlier workflow only uploaded Actions artifacts; public API observation showed a successful Windows run and an empty public Releases list. A separate Ubuntu publication job now consumes the successful same-run artifact on main push/manual events in lahuman/Codex_Monitor, with write permission scoped to that job. It validates the configuration/manifest/checksums and verifies the commit is still main head before remote mutation. A dedicated desktop-v<version>-windows-x64 lightweight tag owns that exact commit. Publication stages three platform-named assets in a draft and verifies server digests (or downloaded bytes when unavailable) before publishing a prerelease, without marking it latest. For example the first successful 0.1.10 main build produces desktop-v0.1.10-windows-x64 with its setup executable and Windows-specific checksum/metadata assets.

A partial draft upload can resume on the same commit; a complete matching public release is a no-op. An existing tag pointing elsewhere, unowned release, conflicting bytes or incomplete public release fails rather than overwriting public state. Changing source for an already released version requires a desktop version bump. Advancing main requires its newer build. Fork/PR/non-main jobs cannot publish. No PAT is required under ordinary repository policies; protected tags or organization token policies may require repository-side decisions. This source change does not run or publish remotely until the user pushes it.
